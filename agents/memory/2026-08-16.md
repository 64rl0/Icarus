# 2026-08-16

## 21:30 — Diagnosed: 3.12.14 install failure on macos14-arm64 is a CPython parallel-install race, not a repo change

**Context:** `Python-3.12.14.install.log` on the macOS 14 build Mac failed 3/3
runs with `make: *** [libinstall] Error 71` + `make: *** [libainstall] Error 71`
right after `Checked 111 modules ... 0 missing` (the build itself was green).
User suspected a recent Icarus change. It isn't one.

---

### Root cause

`build_generic` runs `sudo -E make -j "${ncpu:?}" install`
(`build_runtime.sh:739`). In CPython **3.12+**, three `commoninstall`
prerequisites race to create `lib/python3.X` within milliseconds of each other:

- `libinstall` → `$(LIBDEST)` directly,
- `libainstall` → as intermediate of `$(LIBPL)` (`config-3.12-darwin`),
- `sharedinstall` → `$(BINLIBDEST)` (its `DESTDIRS` loop).

Each does `test ! -d` then `$(INSTALL) -d` — a TOCTOU race. **Apple/BSD
`install -d` exits 71 (EX_OSERR) when its mkdir hits EEXIST**; GNU coreutils
treats it like `mkdir -p` → Linux is immune. In the failing log,
`sharedinstall` won (and went on installing every `.so`), the other two died —
exactly the two `install: mkdir ...: File exists` lines.

Why only 3.12+: **3.10/3.11's `sharedinstall` is `setup.py install`** — slow
interpreter startup + EEXIST-tolerant `os.makedirs`, so there's no fast
three-way `install -d` collision. 3.12 removed setup.py and added the shell
loop. **3.13/3.14 have byte-identical racy machinery** — their green macos14
builds on 08/06 just won the coin flip. They remain exposed.

### Evidence matrix (from `gh release list --repo 64rl0/PythonRuntime`)

| Same day (08/16) | Result |
|---|---|
| 3.12.14 macos26-arm64 (17:13Z), macos15-arm64 (17:58Z) | PASS |
| 3.11.16 + 3.10.21 on the **same macos14 machine** (19:00/19:10Z) | PASS |
| 3.12.14 macos14-arm64, 3 attempts | FAIL |

3.12.0–3.12.12 all built green on macos14-arm64 on 2026-02-15, 3.12.13 on
2026-03-06 — 13 straight wins of the same race.

### Ruled out, with proof

- **Icarus script:** the `-j` install line is unchanged since ≥ June 2025
  (build 2.2.24). The Debian-era diff touches the macOS path in exactly one
  place — `build_uuid_macos`, **3.14 block only**. Since Jan 30 the only
  install-related diff lines are Debian `apt-get` ones.
- **CPython 3.12.14:** `Makefile.pre.in` install targets are byte-identical to
  3.12.13 (diff = expat headers + a `_bootstrap_python` pybuilddir.txt dummy).
- **ncpu:** same `sysctl -n hw.ncpu` computation throughout.

Why it flipped from 13/13 wins to 0/3 on that box is environmental — the log
now stamps `macosx-14.8-arm64` (Feb/Mar builds predate 14.8), so an OS/CLT
update plausibly shifted scheduler timing. Unknowable precisely from here, and
irrelevant to the fix.

### Fix (applied by user, same session — in working tree, uncommitted)

Dropped `-j "${ncpu:?}"` from the **install** line only (`build_runtime.sh:739`):
now `sudo -E make install`. Install is I/O-bound — costs seconds, immunizes
every version/platform including the latent 3.13/3.14 exposure. Compile line
734 keeps `-j`. Verified: no other `make install` in the script, `bash -n` OK.

**Outcome: confirmed.** User updated the macOS 14 build Mac, re-ran, and
3.12.14 built green — root cause and fix both validated end-to-end. The fix
still needs to propagate to the macos15/macos26 build Macs whenever they next
update icarus (they pass today on race luck for 3.13/3.14).

### Lessons

- **`gh release list` is the build ledger.** Release timestamps answered
  "when did X last build on Y" in one command — settled in minutes what log
  archaeology couldn't (workspace is tmpfs/wiped).
- **`git log -S` without `--follow` lies across file moves.** `-S 'sudo -E
  make'` pointed at the Jan 2026 commit, but that was the `cli_scripts/` →
  `src/icarus/cli_scripts/` move; the string dates to ≥ June 2025.
- A 3/3-deterministic-looking failure can still be a probabilistic race whose
  odds shifted; before hunting "the change that broke it", build the
  pass/fail matrix across the other axes (other versions same machine, same
  version other machines).
