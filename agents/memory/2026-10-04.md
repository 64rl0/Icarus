# 2026-10-04

## 13:10 — Diagnosed & fixed: CPython ≤3.12 macOS builds segfault because the Xcode 27 CLT SDK falsely advertises pipe2()/dup3()

**Context:** New Python releases (3.14.x, 3.13.16, 3.12.15, 3.11.17, 3.10.22)
on the macos26-arm64 build host: 3.14/3.13 built fine, 3.12/3.11/3.10 kept
failing with no script or host change. Logs extracted to
`~/Dropbox/SDE/icarus build failure/`.

---

### Root cause

The host's Command Line Tools updated to the **Xcode 27 toolchain**
(clang-2100.3.34.2) via normal Software Update — Xcode majors are not tied to
macOS majors, so no macOS 27 upgrade was involved. The new SDK ships
prototypes for `pipe2()`/`dup3()`, so CPython's configure detects them
(`checking for pipe2... yes` — never true on macOS before), but macOS has no
working implementation → **every subprocess spawn segfaults**:

- PGO run: SIGSEGV in `test_base64` at `subprocess._execute_child`
  (hidden by the Makefile's `|| true`, build continues with truncated profile).
- `make install`: SIGSEGV in `./python.exe -E -m ensurepip` → Error 139 →
  no `bin/pip3` → the later `fix_shebang` "Failed to copy 'pip3'" is fallout.

Why only ≤3.12: upstream fixed it by skipping those configure checks on macOS
(commit `e869134`, in 3.13.15+; dep patch `7d265b6` in 3.13.14). 3.12/3.11/3.10
are security-only and will never get the backport. Same issue: pyenv#3542,
fixed by pyenv PR #3547.

### Fix shipped (in working tree, not yet committed)

`src/icarus/cli_scripts/builder_handler/build_runtime.sh`, in
`build_python_runtime()`'s Darwin "compile CPython" env block (after the
`unset C_INCLUDE_PATH...` line, anchor: the only
`xcrun --sdk macosx --show-sdk-path` in the file):

```bash
if [[ "${python_full_version}" =~ ^3\.(7|8|9|10|11|12)\. ]]; then
    export ac_cv_func_pipe2=no
    export ac_cv_func_dup3=no
fi
```

**Deliberately version-scoped** (user's design call): upstream owns the
behavior for 3.13+ (they might re-enable the syscalls if a future macOS
implements them), and the workaround self-expires when legacy versions leave
the matrix. macOS-only — Linux genuinely has these syscalls and must keep
them. No functionality loss: the fallback (`pipe()`/`dup2()` + fcntl) is what
every macOS Python ever shipped uses; `os.pipe2` never existed on macOS.

Verified on the macos26 host before landing: 3.12.15, 3.11.17, 3.10.22 all
built successfully with the exports in place.

### Lessons

- **`check_python_runtime` has a blind spot:** it only imports modules, never
  spawns a subprocess — a broken-subprocess runtime passes it and still gets
  tarred (release push was only blocked by `exit_code=1` from earlier steps).
  Consider adding a `subprocess.run([sys.executable, "-c", "pass"])` probe.
- `prepare_sysroot_macos` checking that `MacOSX26.sdk` exists pins nothing —
  after a CLT update that name resolves into whatever SDK the new CLT ships,
  and CPython is built with `SDKROOT=$(xcrun --show-sdk-path)` anyway.
- CLT auto-updates via Software Update are a silent toolchain-change vector on
  the build hosts. Pin option: install full Xcode from .xip (not App Store)
  and `xcode-select -s` to it.
- Diagnosis flow that worked: master log → first `exit_code=1` setter →
  per-step logs (`Python-X.configure.log` showed `pipe2... yes` smoking gun).

**Follow-ups:**
- Commit + deploy the fix (user does this via their normal flow).
- Host still on the Xcode 27 CLT; rollback to 26.x CLT optional now that the
  script is fixed.
