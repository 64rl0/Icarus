# 2026-08-10

## 15:21 — Added `--with-thoughts-and-prayers` joke flag to the release target

**Context:** Familiarised with the build system (`builder.sh`, `path.sh`,
`builder_base.sh`, and the argparse chain), then added a hidden joke flag:
`icarus builder release --with-thoughts-and-prayers`. It registers as a hook
that always passes, and on a failed run prints a condolence block after the
summary table.

---

### Decisions / events

**Shape of the feature**

- Implemented as a **real hook** (internal name `prayers`, zero prior
  collisions in the tree) rather than a modifier, specifically so it earns a
  row in the summary table. `prayers | PASS | 0.032s` is the joke: the one hook
  structurally incapable of failing, sitting beside the ones that broke. Also
  bumps the header to `Collected and preparing to run 14 hook(s).`
- `run_prayers` prints `Praying for Python<ver>...` and is **not** `run_once`,
  so it repeats per configured interpreter. It never touches `exit_code` — a
  joke flag must not be able to fail a release.
- **Hidden from `--help`** via `argparse.SUPPRESS`, but documented in
  `site-functions/_icarus` (both the `hook)` and previously-bare `release)`
  blocks) so tab-completion still surfaces it.
- Flag defined once on a **shared parent parser** (pattern already used by
  `amazon auth-init` in `cli.py`) and attached to both the `release` subcommand
  and `hook`, so the two spellings can't drift.

**Validation rule (user was explicit: verbatim forms only)**

Legal *only* as `builder release --with-thoughts-and-prayers` or
`builder hook --release --with-thoughts-and-prayers`. Enforced in two layers:

1. Argparse rejects it on any other subcommand (flag simply isn't defined
   there) → "unrecognized arguments".
2. Guard in `parse_icarus_builder_cli_arg`: rejects unless `release` is set
   **and** `builder_hooks_count <= 2` (2 because release itself is counted).
   New message constant `release_only_arg`.

Deliberate decisions:
- The **hand-spelled release set is rejected** —
  `hook --build --isort --mypy --with-thoughts-and-prayers` fails. Rule is tied
  to the literal `--release` token, not the resulting hook set. Simpler to state.
- Guard placed **after** the existing standalone checks so
  `--pypi --with-thoughts-and-prayers` keeps its clearer "`--pypi` is a
  standalone argument" message.
- `--verbose` still allowed (lives in `base_args`, not counted as a hook) —
  breaking it would be perverse given the HELP block exists to suggest a
  `--verbose` re-run.
- Token *order* is not enforceable without hand-parsing `sys.argv`;
  `hook --with-thoughts-and-prayers --release` is accepted. Judged not worth it.

**Condolence block**

- `echo_prayers` lives in `builder_base.sh` directly **below**
  `echo_help_verbose` as a sibling — same badge/timestamp house style, same
  `1>&2`, but deliberately NOT inside it.
- **Why not inside `echo_help_verbose`** (user initially suggested this, then
  clarified they meant a separate function): it has 13 call sites and *none* is
  a hook failure. Hooks (`run_pytest`, `run_mypy`, …) set FAIL and return
  without calling it. Its real triggers are 2 artifact-path failures and 11
  `resolve_path` aborts. So a normal broken release — red tests, everything
  else fine — would produce **zero** blocks. It also prints once per error by
  design, and the 11 errexit sites kill the script before `echo_summary`, so
  the block would print with no table and a bogus count.
- Messages held in an array, picked with `$RANDOM % ${#messages[@]}`
  (no `shuf`/`seq`, no hardcoded count so adding a 4th needs no other edit).
  Drew 300 samples to confirm all three are reachable and roughly even
  (92/110/98) — a modulo off-by-one would have silently orphaned one.
- Reworded one candidate from "It is the only hook that did" to "It was never
  going to do otherwise", because the original is *false* whenever other hooks
  passed, and the humour depends on being accurate against the table above it.

**Refactor after CR — moved the count into `echo_summary`**

Originally counted failures in a bespoke loop in `dispatch_build_system`. User
asked to move it. This **fixed a bug I had shipped**: my loop iterated
`running_hooks_name`, but the table iterates `all_running_hooks_name`, which
prepends the `index` and `path` rows. `path` *can* fail without aborting (the
two non-errexit sites at `builder.sh:926` / `991`), so a release where only
`path` failed would have printed "0 hook(s) did not make it" directly under a
table showing `path | FAIL`. Counting inside the existing table loop (which
already evals `status` per row) makes the number structurally unable to
disagree with what the user is reading — and costs one `if`, not a second loop.
`dispatch_build_system` is now byte-for-byte back to original.

**Permanent toggle test**

User asked for a test they can flip themselves; left in place.
`test_thoughts_and_prayers_toggle` in `test/test_application.py` — flip
`SHOULD_PASS = True` → `False` to fail on purpose. Follows the file's existing
idiom (`assert <cond>, textwrap.dedent(...)`, same as
`test_that_you_wrote_tests`). Note **pytest reads the working tree**, so this
needs no rebuild — the one exception to the stale-build rule.

### Lessons

- **`pip install .` into `runtime/env` is required to test CLI changes.** First
  end-to-end run failed with "unrecognized arguments" because the runtime still
  had 2.14.16 installed. Earlier tests had passed only because they imported
  `src/` directly. This is exactly the stale-build trap
  `context/build-system.md` documents — and it catches *CLI parser* changes
  too, not just library code.
- **A missing `X_execution_time` initialiser aborts an otherwise-green run.**
  Proved it: `echo_summary` reaches `printf "%.3f" ""` → "invalid number" →
  exit 1 under `errexit`, at the *very last step* after all real work
  succeeded. Both `prayers_summary_status` and `prayers_execution_time` are
  required in `set_constants`. Verified the failure mode deliberately rather
  than trusting the reasoning.
- **W505 caps comment/docstring lines at 72 chars** (not the 100 that `black`
  uses for code). Three of my own comments tripped `flake8` on the first
  release run. Worth pre-checking comment width when adding commentary.
- **Don't trust a subagent's bug report without reproducing it.** A subagent
  claimed `run_mypy`'s `if [[ "${?}" -eq 1 ]]` inside `|| { }` always sees a
  clobbered `$?`, so mypy failures never register. **False** — tested with the
  exact code shape: `$?` survives into the guard and exit 1 sets FAIL
  correctly. (Real but minor: exit code 2, mypy's internal error, *is*
  swallowed.) Reporting that unverified would have been worse than saying
  nothing.
- **Quote test-harness args properly.** A rejection-matrix loop passed
  `"hook --release --mypy"` as a single argv element, producing "invalid
  choice" instead of the real validation error and briefly looking like the
  guard was broken.
