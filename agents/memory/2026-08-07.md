# 2026-08-07

## Session — Debian 13 support in `build_runtime.sh` + fixing silent build gates

**Context:** `build_runtime.sh` (2550 lines, `src/icarus/cli_scripts/builder_handler/`)
built portable CPython runtimes for macOS and yum distros (centos9, amzn2023,
amzn2) only. Task was to add Debian 13 (trixie) as a target. Build host is
`debian13-aarch64` — note **aarch64**, the first Linux arm64 target; existing
Linux runtimes are x86_64.

---

### Decisions / events

**Debian port — mechanism**

- `yum --installroot` has no apt equivalent. Evaluated four options; chose
  **`mmdebstrap --variant=extract`**. Rejected: `apt-get -o RootDir=` (cannot
  bootstrap from empty), `debootstrap` (runs maintainer scripts, takes host
  locks), `--variant=custom` (needs a working `dpkg` inside the chroot — fails).
- **Separate functions, not modified shared ones**, per user preference: new
  `prerequisites_for_debian`, `prepare_sysroot_debian`,
  `build_debian_base_dependencies`, `check_loadable_refs_debian`,
  plus helpers `linux_pkg_family`, `linux_multiarch_triplet`, `debian_codename`.
- **Gating:** version-block dispatch gates on `*'debian13-'*` (explicit, per
  user request — a future Debian must be added deliberately). The three
  sysroot/env/check dispatchers gate on `linux_pkg_family` (apt vs yum) since
  that distinction is genuinely package-manager-level. All raise on unknown.
- Debian sysroot is deliberately **minimal — 4 packages** (`libc6-dev`,
  `linux-libc-dev`, `libgcc-s1`, `libstdc++-<gcc major>-dev`). The yum sysroot
  also installs bash/coreutils/gcc/make; nothing is ever *executed* from a
  sysroot (consumed only via `--sysroot`, deleted by `clean_build`), so minimal
  is both sufficient and more pollution-proof. **This choice has downstream
  consequences — see the `nis` bug below.**
- `libstdc++-N-dev` derives from `gcc -dumpversion`, not hardcoded.

**Bugs found and fixed (all pre-existing except where noted)**

1. **`exit_code=1` lost in subshells** — `find | while` puts the loop body in a
   subshell, so every `exit_code=1` was discarded. Affected
   `check_loadable_refs_{macos,linux,debian}`, `check_broken_links` (which also
   lost `broken_links`, so its `echo_error` never fired) and
   `fix_runtime_paths_linux`. Fixed with `while ... < <(find ...)`.
   **This is the most consequential find of the day** — it means every yum and
   macOS build has been passing these gates vacuously. Also converted
   `fix_runtime_paths_macos` for consistency (no live bug there; proved
   behaviour-identical with a stubbed `install_name_tool` harness).
2. **No `echo_error` in `check_loadable_refs_*`** — they set `exit_code` but
   printed only a bare `Match case` line. Added a `bad_refs` flag +
   `echo_error`, matching how `check_broken_links` already worked.
3. **Sysroot scanned by the gates** — `check_loadable_refs_*` had no
   `-prune` for the sysroot (unlike `fix_runtime_paths_*` which do). On AL2023
   the sysroot contains **6 32-bit i386** multilib libs from gcc; x86_64 `ldd`
   can't parse them, hits the `ldd_failed` branch → build failed with no
   `Match case`. Pruned in all three gates.
4. **`libharfbuzz-cairo` unloadable** — the bare `"libharfbuzz"` allowlist glob
   also matched `-cairo`, which needs `libcairo` (not shipped, not on the build
   hosts). Fixed by tightening the entry to `"libharfbuzz.so"` on **both**
   Debian and yum. Confirmed pre-existing: the already-published
   `cpython-3.13.14-amzn2023-x86_64` ships the same broken file.
5. **glib developer tools shipped on Debian** — the yum entries
   `"girepository"`/`"glib"` match only `libglib*.so` on RPM, but on Debian
   `usr/lib/<triplet>/glib-2.0` is a *directory of executables*. Shipped 5
   host-linked binaries dragging in libgio/libgmodule/libmount/libblkid/
   libselinux. Removed those bare entries.
6. **`libgirepository` dropped on Debian** — nothing in the runtime loads it
   and it was the sole consumer of those five host libs.
7. **`nis` missing on Debian ≤3.12** — see the dedicated section below.
8. **`/lib` symlink missing in the Debian sysroot** — glibc ships `libc.so`
   and `libm.so` as **ld scripts with absolute paths**
   (`GROUP ( /lib/<triplet>/libc.so.6 ... )`). `ld` resolves those *inside* the
   sysroot; `--variant=extract` runs no maintainer scripts so the usrmerge
   symlinks don't exist. Every link failed with the opaque autoconf message
   "C compiler cannot create executables". Fixed with
   `--extract-hook='for d in lib bin sbin; do ln -sfn "usr/${d}" "${1}/${d}"; done'`.
   The shipped `merged-usr` hook and `--include=usrmerge` are both **no-ops**
   here (the hook only relocates a top-level dir that already exists).
9. **`cmake` metadata shipped** — added `"cmake"` to `dirs_to_clean` and
   `"*.cmake"` to `files_to_clean` (two shapes: `lib/cmake/OpenSSL/` and
   `lib/libpng/*.cmake`).
10. **`check_hardcoded_paths` hardcoded usernames** — added `admin`, `debian`,
    `/home/admin`, `/home/debian` (Debian cloud images default to `admin`).
    Note: user explicitly asked for **hardcoded literals**, not a
    `SUDO_USER`-derived list (I proposed the latter first; it was rejected as
    over-engineered).

**The `nis` bug on Debian ≤3.12 — worth understanding fully**

3.13/3.14 built clean; every 3.12 build failed with
`check_python_build_logs` → "necessary bits ... not found: nis".
`nis` was **removed from CPython in 3.13 (PEP 594)**, hence the exact version
boundary.

Root cause was **two** things, and fixing only the first was not enough:

1. `build_libnsl` was not called on Debian for 3.10–3.12. I had originally
   skipped it with a comment claiming "Debian ships libnsl-dev so it's not
   needed". That was wrong. Mirroring centos9/amzn2023 (adding `build_libnsl`)
   was necessary.
2. **The real blocker:** CPython's probe is
   `PKG_CHECK_MODULES([LIBNSL],[libnsl])` falling back to
   `AC_SEARCH_LIBS([yp_match],[nsl])`. That link pulls
   `libnsl → libtirpc → libgssapi_krb5 → krb5 stack`, and `ld` resolves those
   transitively **inside the sysroot**. The minimal Debian sysroot has none of
   them → `checking for library containing yp_match... no` → nis missing.
   Fixed by adding **6 entries** to the Debian allowlist: `libcom_err`,
   `libgssapi_krb5`, `libk5crypto`, `libkeyutils`, `libkrb5` (its glob also
   covers `libkrb5support`).

The yum sysroot installs `gcc`/`glibc-devel`, which happen to drag the krb5
stack in — which is why centos9/amzn2023 never needed those entries. **The
minimal Debian sysroot is the reason this surfaced.**

**Explicit decision: krb5 stays transitive on yum**

User decision, after I laid out the trade-off: **do not** add krb5 to the yum
allowlist, to avoid rebuilding 150+ existing artifacts.

Accepted known limitation: yum ≤3.12 artifacts reference
`libgssapi_krb5`/`libkrb5`/`libk5crypto`/`libcom_err` via `libtirpc` with **no
shipped provider** — they resolve from the host. `import nis` would fail on a
host without krb5. Safe today because every yum target is RHEL-family where
`krb5-libs` is base. Notably **Debian's `libgssapi-krb5-2` is
`Priority: optional`** (pulled in incidentally by openssh) — so the assumption
is much weaker there, which is another reason Debian ships them.

If it ever bites: the fix is the same 6 entries, applied to the yum allowlist.

### Lessons

- **`find | while` silently swallows variable assignments.** Any check that
  reports failure by setting a flag inside such a pipeline is vacuous. Use
  `while ... < <(find ...)`. This had made four separate gates decorative.
- **Verify probes replicate real build conditions.** I twice reached a wrong
  conclusion from a badly-set-up probe: (a) reported `_tkinter` as the missing
  3.12 module because my probe pulled Tcl/Tk from `tk-dev` (headers in
  `include/tcl8.6/`) instead of building from source into `local/include/`;
  (b) claimed a build-order bug from file mtimes when the stage log showed the
  order was correct (the gap was just `make install` finishing later). Both
  were caught only by continuing to test.
- **`sed -n '/local -a libs=(/,/^    )/p'` matches BOTH allowlists** (yum and
  Debian each have one). Scope extraction to the enclosing function first, or
  you validate the wrong array — this produced two misleading verification runs.
- **An unreferenced `.so` with an unresolvable dependency is harmless.** The
  dynamic loader is lazy: it only resolves libraries something actually loads.
  Proved by deleting `libharfbuzz-cairo.so*` from a built runtime — everything
  still worked. This is why the ~150 existing artifacts did **not** need
  rebuilding. `ldd` reports the breakage only because you explicitly ask it to.
- **Don't reason circularly from an existing allowlist.** I initially justified
  "leave krb5 transitive on yum" partly because the check's allowlist blesses
  those libs — but that entry just documents the original author's assumption
  about RHEL hosts. It isn't evidence the assumption generalises.
- **Prefer tightening an existing mechanism over adding a second one.** I first
  excluded `libharfbuzz-cairo` with `rsync --exclude`; user pushed back, and the
  right fix was a more precise allowlist prefix (`"libharfbuzz.so"`). One
  mechanism, intent visible where you'd look for it.
- **Read `config.log`, not the autoconf summary.** "C compiler cannot create
  executables" was really
  `ld: cannot find /lib/<triplet>/libc.so.6 inside <sysroot>`.

      3.11 and 3.10 share the fix but are unverified. Confirm
      `Checked ... modules` shows `0 missing` on at least one.

      (L3078) while the repo has `false`. It deletes every log on success *and*

      several rebuilds. Worth reconciling.
- [ ] **`libnsl`/`libtirpc` are dead weight on 3.13+** on both platforms
      (verified: nothing links `libnsl` in the AL2023 3.14 artifact). Gating
      them to ≤3.12 would shrink artifacts, remove the yum krb5 exposure for
      future builds, and silence the recurring
      `Failed to copy '.../usr/lib64/libnsl'` warning.
- [ ] **`max_parallel=10`** on a 64-core host with `/tmp` on a **62G tmpfs** and
      ~1.1G per build tree. Suggest 2–3. Symptom if it bites on apt:
      nine of ten jobs dying instantly on
      `Could not get lock /var/lib/dpkg/lock-frontend`.
- [ ] **Pre-existing, not mine to fix:** `check_python_build_logs` is skipped on
      macOS for 3.10/3.9/3.8 and on Linux for 3.7 — those builds run with one
      fewer gate. Also `set_ownership` uses
      `groups "$u" | awk '{print $1}'` (returns the *username*; `id -gn` is
      correct — works only because both distro families create user-private
      groups). Also the **yum** allowlist has a real `SC2221/2222`
      pattern-overlap bug (`/lib/libc*` shadows `/lib/libcom_err*`), harmless
      because both are allowlisted.
- [ ] **Build-host quirk:** `LC_ALL=en_US.UTF-8` is set on the Debian box but
      that locale isn't generated, so perl/bash warn on every command and
      pollute build logs.

### Env notes (non-secret)

- Build hosts are reachable over SSH with the key at
  `~/Dropbox/SDE/Secrets/ssh-keys/` (path only — do not record IPs/keys here;
  they change). SSH user differs per distro: `admin` on Debian, `ec2-user` on
  CentOS/AL2023.
- All build hosts keep the workspace under `/tmp/icarus-root/build-runtime/`,
  and `/tmp` is **tmpfs** — everything is lost on reboot. Snapshot logs before
  re-running anything, since `main()` also wipes
  `python_version_build_root` at the start of each run.
- Useful: `.../workspace/<ver>/build_<ver>.log` for stage flow;
  `.../workspace/<ver>/log/Python-<ver>.{configure,make,install}.log` and
  `.../tmp/<platform>/<Pkg>/config.log` for real compile errors.
